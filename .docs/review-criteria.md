# レビュー基準チェックリスト

プルリクエスト（PR）ごとに、変更の影響範囲に応じて以下を確認する。該当しない項目は理由を記載してスキップし、未確認の項目を承認条件に残さない。`[x]` はCIなどにより自動実行・確認される基準を示し、個別変更での判断が必要な項目は `[ ]` のままとする。`（…）` はGitHub Actionsで追加できる自動チェックの候補である。

## 自動化方針

- 手動レビュー項目は、GitHub Actionsで検証可能な形へ継続的に移行する。
- `（…）` の候補は、優先的な導入対象としてIssueまたはPRにする。
- 自動化できない項目や誤検知が多い項目は、人がレビューする。
- 自動チェックを導入した項目は、根拠リンクを添えて `[x]` に更新する。

## 1. 要件・仕様

- [ ] 目的、対象ユーザー、受け入れ条件がPR本文または関連Issueで明確になっている。
- [ ] 正常系だけでなく、入力不足・不正値・空データ・権限不足時の期待動作が定義されている。
- [ ] 既存仕様との互換性、破壊的変更、移行手順、ロールバック方法が明記されている。
- [ ] 仕様変更に伴うスキーマ、APIドキュメント、テスト、サンプルの更新漏れがない。`（変更ファイル整合性チェック）`
- [ ] 実装範囲が目的に対して過不足なく、無関係なリファクタリングを含んでいない。

## 2. コード品質

- [ ] 変数名・関数名・型名が役割を表し、略語や曖昧な名前を避けている。
- [ ] 1つの関数・コンポーネントが単一の責務に収まり、深いネストや重複ロジックがない。`（ESLint複雑度・重複ルール）`
- [ ] TypeScriptの型を活用し、`any`、不要な型アサーション、暗黙のnull/undefined依存がない。`（typescript-eslintルール）`
- [ ] エラー処理、境界値、非同期処理の失敗・キャンセル・再試行を適切に扱っている。`（Vitest失敗系テスト）`
- [ ] コメントは「何をするか」の繰り返しではなく、判断理由や制約を説明している。
- [ ] 既存のフォーマッター、リンター、命名、インポート順の規約に従っている。
- [ ] 変更は最小限で、既存のユーザー変更や無関係なファイルを巻き戻していない。

## 3. 設計・アーキテクチャ

- [ ] 変更箇所が責務の所在に合っており、依存方向やレイヤー境界を越えていない。
- [ ] WebのAPI呼び出しは `apps/web/src/api.ts` に集約し、コンポーネント内に直接 `fetch` を追加していない。`（ESLint禁止パターン）`
- [ ] サーバー状態はTanStack Queryで管理し、キャッシュキー、無効化、ローディング、エラー状態が整合している。
- [ ] 共有するデータ契約や型は適切なパッケージに置き、同じ定義を複数箇所で複製していない。
- [ ] 状態管理、キャッシュ、イベント購読に不要な再計算・再レンダー・メモリ保持がない。
- [ ] DBスキーマ変更には新規Prisma migrationがあり、既存migrationを書き換えていない。`（Prisma migration差分チェック）`
- [ ] 将来の拡張、障害時の観測性、性能上のボトルネックを必要な範囲で考慮している。

## 4. UI・アクセシビリティ

- [ ] UIはStyleXを標準手段として使い、既存のデザイン・余白・色・タイポグラフィと整合している。`（ESLint・StyleXビルド検査）`
- [ ] コンポーネントがローディング、空状態、エラー、成功、無効状態をユーザーに伝えている。`（Playwright状態テスト）`
- [ ] キーボードだけで操作でき、フォーカス順・フォーカス表示・Escape等の操作が自然である。`（Playwrightキーボード操作）`
- [ ] ボタン、入力、ダイアログ、通知に適切なセマンティック要素とラベルを使用している。`（Playwrightアクセシビリティ検査）`
- [ ] 色だけに依存せず、コントラスト、文字サイズ、スクリーンリーダー向け名称を確認している。
- [ ] レスポンシブ表示、長い文字列、狭い画面、表示倍率変更でレイアウトが破綻しない。`（Playwright複数ビューポート）`
- [ ] 送信・削除などの重要操作は二重送信防止と結果のフィードバックを備えている。`（Playwright操作テスト）`

## 5. API・データ契約

- [ ] リクエスト・レスポンスをZodで検証し、検証失敗時に一貫したエラー形式とHTTPステータスを返している。`（Vitest API契約テスト）`
- [ ] 公開エンドポイントを `@hono/zod-openapi` のOpenAPI契約へ登録している。`（OpenAPIルート整合性テスト）`
- [ ] `/api/doc` の仕様が実装、型、認証要件、エラー応答と一致している。`（OpenAPIスナップショットテスト）`
- [ ] 入力のサイズ、形式、許容値、ページング、ソート、フィルターをサーバー側でも制限している。`（Vitest境界値テスト）`
- [ ] 認証・認可を各保護エンドポイントで確認し、IDを知っているだけで他ユーザーのデータに到達できない。`（Vitest認可テスト）`
- [ ] 後方互換性、nullability、日時・数値・列挙値の表現がクライアントと合意されている。
- [ ] 外部サービスやDBのタイムアウト、再試行、部分失敗、トランザクション境界を明確にしている。

## 6. テスト・検証

- [ ] 受け入れ条件を再現するユニットまたは統合テストがあり、重要な境界値・失敗系も含んでいる。`（Vitestテスト実行）`
- [ ] API契約やビジネスロジックの変更にVitestのテストを追加・更新している。`（Vitest実行・カバレッジ）`
- [ ] 重要なUI利用フローの変更にPlaywrightのE2Eテストを追加・更新している。`（Playwright E2E実行）`
- [ ] テストは実装詳細ではなく、ユーザーから観測できる振る舞いと契約を検証している。
- [ ] テストデータ、時刻、乱数、外部依存を制御し、テストが順序や実行環境に依存していない。
- [x] `npm run format:check`、`npm run lint`、`npm test`、`npm run build` を変更範囲に応じて実行し、結果を記録している。 (`package.json`, `.github/workflows/quality.yml`)
- [ ] E2Eまたは統合テストを省略した場合は、理由と代替検証をPR本文に記載している。

## 7. セキュリティ・プライバシー

- [ ] ユーザー入力を信頼せず、検証・認可・出力エスケープを適切な境界で行っている。`（Semgrep入力検証・危険シンクルール）`
- [ ] SQL、コマンド、HTML、URL、ログへのインジェクション経路がなく、危険な文字列連結をしていない。`（Semgrepインジェクション・文字列連結ルール）`
- [ ] 認証情報、トークン、個人情報、秘密鍵をコード・ログ・エラーメッセージに含めていない。`（Semgrep秘密情報・機密ログルール）`
- [ ] 最小権限、テナント分離、CSRF/CORS、レート制限、リプレイ対策を変更の性質に応じて確認している。
- [ ] ファイルアップロード、リダイレクト、外部URL、Webhook、デシリアライズの入力を制限している。`（Semgrep危険API・外部URLルール）`
- [ ] 依存関係の追加・更新に目的、利用箇所、代替しない理由と既知の脆弱性確認がある。`（npm auditと依存差分検査）`
- [x] セキュリティ変更では `npm run semgrep` を実行し、検出結果を確認している。 (`package.json`, `.semgrep.yml`, `.github/workflows/quality.yml`)

## 8. 性能・信頼性・運用

- [ ] DBクエリに適切なインデックス、ページング、取得列の絞り込みがあり、N+1を起こしていない。
- [ ] 大量データ、同時実行、遅いネットワーク、再接続、タイムアウト時の挙動を確認している。
- [ ] ログ・メトリクス・トレースに障害原因を特定できる情報があり、機密情報をマスクしている。
- [ ] エラーを握りつぶさず、利用者向けメッセージと運用者向け詳細を分離している。`（Semgrep空catch・例外握りつぶしルール）`
- [ ] リソース（接続、タイマー、購読、キャッシュ）を適切に解放し、再実行時に重複処理しない。`（ESLintリソース管理ルール）`
- [ ] デプロイ順序、環境変数、migration、フィーチャーフラグ、監視とロールバック手順を確認している。

## 9. ドキュメント・レビュー運用

- [ ] README、API仕様、設計メモ、コメント、変更履歴のうち影響を受けるものを更新している。
- [ ] 新しい環境変数は `.env.example` に説明付きで追加し、`.env` や秘密情報をコミットしていない。`（変更差分・秘密情報スキャン）`
- [ ] PR本文に概要、変更理由、テスト結果、既知の制約、残る判断事項を記載している。
- [ ] レビューコメントは再現手順・期待結果・優先度を添え、対応済みか未対応かを追跡できる。
- [ ] 指摘対応後に差分を再確認し、修正が別の仕様・テスト・セキュリティ要件を壊していない。
- [ ] 承認前に未解決の重大指摘、失敗した必須検証、未確認の破壊的変更が残っていない。
